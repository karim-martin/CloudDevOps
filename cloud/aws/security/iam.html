AWS IAM

AWS

Identity and Access Management — control access to every AWS service.

IAM = The Bouncer for Every AWS Door

Every action in AWS — reading from S3, launching EC2, connecting to RDS — requires permission. IAM controls these permissions. An IAM Role is a set of permissions you can assign to an AWS service (your EC2 instance, Lambda, or EKS pod). A Policy is a JSON document listing what's allowed. The golden rule: least privilege — grant only the minimum permissions needed.

IAM Concepts

👤

IAM Users

Human users with permanent credentials. Best practice: don't use for apps — use Roles instead. Enable MFA for all human users.

🎭

IAM Roles

Assumed by services (EC2, Lambda, EKS pods). Temporary credentials auto-rotated. No long-lived secrets. Always prefer roles over users for applications.

📋

IAM Policies

JSON documents that define permissions. Attach to roles/users/groups. AWS provides managed policies; you can create custom ones.

🔗

IRSA (for EKS)

IAM Roles for Service Accounts. Maps a Kubernetes Service Account to an IAM Role so pods get AWS permissions without any credentials.

IAM Policy Example

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::my-app-uploads/*"
    },
    {
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:us-east-1:123:secret:myapp/*"
    }
  ]
}

IRSA — EKS Pod IAM Access

# 1. Enable OIDC provider for your EKS cluster
eksctl utils associate-iam-oidc-provider \
  --cluster my-cluster --approve

# 2. Create IAM role with trust policy for the service account
eksctl create iamserviceaccount \
  --cluster my-cluster \
  --namespace production \
  --name backend-sa \
  --attach-policy-arn arn:aws:iam::123:policy/MyAppPolicy \
  --approve

# 3. Use in Kubernetes deployment
# spec.serviceAccountName: backend-sa
# The pod now has AWS permissions — no credentials needed!
